# Consumer migration guide

## Standalone server

Install workspace dependencies from the repository root, choose an absolute temporary SQLite path, and run:

```powershell
$MspRoot = (Resolve-Path '.').Path
$env:MSP_DB_PATH = (Join-Path $env:TEMP 'msp-smoke.sqlite')
if (-not [IO.Path]::IsPathRooted($env:MSP_DB_PATH)) { throw 'MSP_DB_PATH must be absolute' }
node .\apps\msp-server\bin\msp-server.mjs
```

The process communicates only through newline-delimited JSON-RPC on stdin/stdout. Absence of `MSP_DB_PATH` is a startup error.

## Package consumer

For a durable local dependency, resolve the MSP checkout explicitly and install
the client from that path:

```powershell
$MspRoot = (Resolve-Path 'C:\path\to\msp-ki17').Path
if (-not [IO.Path]::IsPathRooted($MspRoot)) { throw 'MSP checkout path must be absolute' }
npm install --save "$MspRoot\packages\msp-client-js"
```

The GoVibe MSP exports then re-export the client symbols from `@freshair129/msp-client-js`. The deprecated local `gks-client.mjs` shim remains in GoVibe because it is a separate fail-closed compatibility surface.

### `close()` now returns a promise

Shipped in `@freshair129/msp-client-js` 0.2.1 (additive on top of 0.2.0's environment allowlist).

`createMspStdioCaller(...).close()` used to return `undefined` after sending the
kill request; it now returns a promise that resolves once the runtime process
has actually exited. Existing callers need no change — ignoring the return value
behaves exactly as before.

Await it if you then touch the runtime's SQLite database, or delete the
directory holding it, from your own process. The killed runtime keeps the WAL
index (`<db>-shm`) memory-mapped until the OS finishes tearing it down, and
inside that window Windows refuses both a fresh connection (as
`SqliteError: disk I/O error`, `SQLITE_IOERR_TRUNCATE`) and the directory's
removal (`EPERM`). See
[`NOTES.md`](NOTES.md#better-sqlite3-13-on-node-24-two-failure-modes-and-what-each-one-was).

```js
await call.close();
// the database file and its -wal/-shm sidecars are free from here
```

## GenesisRAG17 relay handoff

GenesisRAG17 is an additional authenticated relay surface and does not replace
the frozen `msp_memory_*` or legacy `msp_*` tools. MSP owns runtime grants,
scope/role checks, downstream response validation, count-only journaling and the
Tier 4 query hop. It owns no stage, source payload, pipeline cursor, canonical
decision, worker result, gate verdict or publication pointer.

The source role may call `msp_pipeline_submit`, `msp_pipeline_evidence` and
`msp_pipeline_query`. The worker role may call `msp_pipeline_claim`,
`msp_pipeline_graph_receipt`, `msp_pipeline_write_receipt`,
`msp_pipeline_gate`, `msp_pipeline_publication_receipt`,
`msp_pipeline_stage_failure` and `msp_pipeline_query`. Both roles are bound by
`MSP_PIPELINE_PRINCIPALS` to an exact six-field private scope. Caller `actor`
and caller-supplied credentials never select authority.

Use [GENESISRAG17-RELAY](GENESISRAG17-RELAY.md),
[ADR-MSP-GENESISRAG17-RELAY](ADR-MSP-GENESISRAG17-RELAY.md), and the
[isolated relay runbook](RUNBOOK-GENESISRAG17-LOCAL.md) for the contract,
extension rules and explicit synthetic environment. The machine schema is
[`packages/msp-contracts/schemas/GENESISRAG17.tools.json`](../packages/msp-contracts/schemas/GENESISRAG17.tools.json).
The cross-repository wire authority is the [zuri-ai contract](https://github.com/Freshair129/zuri.ai/blob/codex/ki17-integration/docs/plans/GENESISRAG17-CONTRACT.md),
and raw-to-publication acceptance is pinned to [commit `b64b46df`](https://github.com/Freshair129/zuri.ai/commit/b64b46df057d3160c659afa3c34628ee86520257).

There is no additional MSP pipeline migration: the relay does not persist
source, decision or worker payloads. zuri-ai owns raw/parsed/chunk lineage,
GKS owns canonical pipeline records, and GenesisBlock owns physical candidate
and publication state. A new field or operation is a coordinated contract
change across those repositories; it cannot be smuggled through the legacy
memory tools or an unvalidated caller field.

## Database schema migration runner

### Foreign-keys=off mode (WP-E0)

`packages/msp-storage/src/db/migrate.mjs` applies every `migrations/NNNN_*.sql` file inside `db.transaction(() => db.exec(file.sql))`, and `connection.mjs` always opens the database with `PRAGMA foreign_keys = ON`. Under those two facts, rebuilding a table that other tables reference by foreign key -- the standard `CREATE ..._new`, `INSERT ... SELECT`, `DROP`, `RENAME` sequence, run inside that transaction -- fails once a **child** row (a row in a table that references the one being rebuilt) exists: `DROP TABLE` on a table other rows still reference performs an implicit delete the still-enabled foreign keys refuse, and `PRAGMA foreign_keys` cannot be changed while a transaction is open. Parent rows alone, or rebuilding a table nothing references, are not at risk from this on their own -- what matters is whether anything points *at* the table being rebuilt.

**The safe rebuild order, and why the other order is unsafe even with zero rows.** The safe sequence is: `CREATE TABLE <table>_new (...)` → `INSERT INTO <table>_new SELECT ... FROM <table>` → `DROP TABLE <table>` → `ALTER TABLE <table>_new RENAME TO <table>`. Do **not** rebuild by renaming the old table away first (`ALTER TABLE <table> RENAME TO <table>_old` → create a new `<table>` → copy → drop `<table>_old`): on the SQLite version this project bundles, `ALTER TABLE ... RENAME TO` rewrites every other table's `REFERENCES <table>` clause to follow the rename, **regardless of whether `PRAGMA foreign_keys` is ON or OFF**. A child table rebuilt with the "rename away" order ends up with its `REFERENCES` clause pointing at the now-dropped `<table>_old`, and `PRAGMA foreign_key_check` alone cannot catch this when the child table happens to be empty at migration time -- the common case for every fresh database and every first boot -- because that pragma only inspects existing rows, not schema. The runner therefore refuses to commit any directive migration that leaves a foreign key pointing at a table that no longer exists, or at a column set that is not the target's PRIMARY KEY or covered by a UNIQUE index, whether or not any row currently exercises it.

A migration file whose **first line is exactly** `-- msp-migration: foreign-keys=off` opts into this mode instead of the plain path:

1. Refuse, with a message prefixed `migration_in_transaction_refused:`, if the connection is already inside a transaction -- `PRAGMA foreign_keys` cannot be changed there, so this mode cannot run nested inside one. No foreign-key check runs in this case, which is why it gets its own prefix rather than reusing `migration_foreign_key_check_failed:`.
2. `PRAGMA foreign_keys = OFF` runs outside any transaction, then is read back and the migration is refused if it did not actually turn off. SQLite ignores the pragma inside a transaction, and better-sqlite3 does not raise an error if you try anyway, so getting the ordering right is the whole point.
3. `PRAGMA foreign_key_check` runs once **before** the migration's SQL executes. Any violation here predates this migration -- an earlier directive migration, or out-of-band tampering -- and is reported as `migration_preexisting_foreign_key_violation:` rather than blamed on this migration.
4. Inside the same `db.transaction(...)` every migration already runs in: the migration's SQL executes, then two checks run in order --
   - a **structural** check across every table in the schema (not just the tables this migration's SQL touched): every foreign key's target table must still exist, every explicitly named target column must exist on it, and the target column set must actually be a key on that table (its PRIMARY KEY, or covered by a UNIQUE index). This is what catches the "rename away" mistake above even when the referencing table is empty.
   - `PRAGMA foreign_key_check`, which must return zero rows -- the row-level case, e.g. an orphaned child row a rebuild's `INSERT ... SELECT` failed to carry forward.
5. Either failure throws the existing `SchemaVersionError` (`code = "db_unavailable"`; no new error code is introduced) with a message prefixed `migration_foreign_key_check_failed:` naming the migration file and the offending table. Throwing inside the transaction rolls back the migration's SQL, so the database is left exactly as it was and the migration is never recorded in `schema_migrations`.
6. Otherwise the `schema_migrations` row is inserted and `PRAGMA user_version` is bumped -- exactly as the plain path does today -- and the transaction commits.
7. In a `finally`, `PRAGMA foreign_keys` is restored to the value read in step 2 -- in practice `ON`, since `connection.mjs` always enables it, but the runner restores whatever it actually was, not a hardcoded `ON`.

A migration author must use this directive on any migration that rebuilds a table other tables reference by foreign key, once the database can already hold rows that reference it. A plain `ALTER TABLE ... ADD COLUMN` does not need it. A migration file without the directive text at all is applied exactly as before, on the plain path; the directive is part of the migration file's own text, so the existing checksum-drift guard covers it automatically, with no special case in the guard itself.

**Any header line that talks to the runner must be exactly right, or startup refuses.** The runner scans the file's leading comment block -- every line from the top (after an optional UTF-8 byte-order mark on line 1) that is blank or starts with a `--` comment, up to the first line that is neither -- for any line that mentions `msp-migration` (case-insensitively, anywhere in the line) and is not exactly the directive on the file's first line. That single rule covers every way a header line can be near, but not exactly, right: a misspelled directive on line 1 itself (missing space after `--`, an underscore instead of a hyphen, spaces around `=`, a missing or doubled space after the colon), the directive on the wrong line, a leading BOM in front of an otherwise-exact line 1, leading or trailing whitespace, different casing, and even a prose comment that only talks about the directive, for example `-- see msp-migration directive docs`. All of these are refused, not silently ignored or run on the plain path -- the header is reserved for the runner, so a line there that merely name-drops `msp-migration` without being exactly right is far more likely a mistake than a deliberate comment. The runner throws `migration_directive_misplaced:`, naming the file and quoting the offending line verbatim, rather than quietly running the migration on the plain path against a table that likely still holds rows the author meant to protect. Content outside the leading comment block -- the SQL body, or a comment after the file's first non-comment statement -- is never scanned, so a migration that mentions `msp-migration` only there still runs on the plain path. A file whose leading comment block never mentions `msp-migration` at all is unaffected; none of root migrations `0001`-`0007` does.

The failures this mode can produce are all the existing startup `SchemaVersionError` (`code = "db_unavailable"`) -- the server refuses to start rather than run against a schema it cannot prove is internally consistent -- distinguished only by message prefix, the same way the checksum-drift and downgrade guards each have their own recognizable prefix: `migration_foreign_key_check_failed:` (the structural check or SQLite's own key resolution failed, on either path), `migration_preexisting_foreign_key_violation:` (a row-level violation predating this migration, directive path only), `migration_preexisting_structural_violation:` (a structural violation predating this migration, either path -- see the plain-path section below), `migration_directive_misplaced:` (a header line near-misses the directive), and `migration_in_transaction_refused:` (the directive migration ran while the connection was already inside a transaction, before any check could run).

See `docs/DESIGN-SESSION-EPISODIC-INSTANCE-MEMORY.md` §12.0 for the motivating case and [`docs/NOTES.md`](NOTES.md#known-source-facts-and-gaps) for exactly which of root migrations 0003's and 0005's rebuilds carried real foreign-key risk, and which did not. `migrations/0008_thread_memory.sql` (TASK-MEMOS-002 stage 1) shipped as brand-new `CREATE TABLE` statements only, never a rebuild of an existing table, so it does not need this mode; a principal-vaults rebuild, if one is still needed, is a later migration.

### The structural foreign-key check now also runs on the plain path (RKOI follow-up warning 2)

**Header scanning can never catch every mistake, so the guarantee no longer depends on it.** The `migration_directive_misplaced:` guard above only fires when a leading-comment-block line contains the substring `msp-migration`. Several header shapes never reach that guard at all and were, until this change, classified `plain` and applied with no structural check whatsoever: a C-style `/* msp-migration: foreign-keys=off */` comment (the scanner only recognizes `--` line comments), a `/* header */` comment sitting ahead of an otherwise-correct directive (the scanner stops at the first non-`--` line, before ever reaching the directive), a leading real `PRAGMA foreign_keys = OFF;` statement (not a comment at all), or a marker misspelling that does not even contain the substring `msp-migration` (`msp_migration`, `msp migration`, `msp-migraton`). Every one of these reaches the plain path with no directive, and on the SQLite version this project bundles, the unsafe "rename the old table away" rebuild order (see above) commits cleanly through the plain path whenever the referencing table is empty -- which it is on every fresh database and every first boot. The server then boots, and the first insert into the referencing table fails with `no such table`, naming the dropped `<table>_old`.

The fix puts the guarantee on the plain path itself: `runMigrations` now calls the same `checkForeignKeyTargetsStructurallyValid` function used by the directive path -- after `db.exec(file.sql)` and before the `schema_migrations` insert and `user_version` bump, inside the plain path's own transaction -- for **every pending migration, directive or not**. A failure throws the same `migration_foreign_key_check_failed:`-prefixed `SchemaVersionError` and rolls the migration's DDL and DML back together, exactly as it already did on the directive path. The row-level `PRAGMA foreign_key_check` is deliberately **not** added to the plain path: with `PRAGMA foreign_keys` always `ON` there, row-level violations are already refused per statement as they happen, and a whole-database row check on every ordinary migration would make any database that already holds one pre-existing orphaned row unable to apply its next migration at all -- a regression explicitly out of scope.

**The directive is still required, but only to relax row-level enforcement for a parent rebuild on a populated database.** The structural check alone cannot make the unsafe rebuild order safe when the referencing table already holds rows: `DROP TABLE` on a table other rows still reference is refused by SQLite itself while `PRAGMA foreign_keys` is `ON`, and that pragma cannot be turned off mid-transaction. A migration that rebuilds a table other tables reference by foreign key, once the database can already hold rows that reference it, still needs `-- msp-migration: foreign-keys=off` for that reason -- the structural check on the plain path is a floor that catches the "empty table" case with no directive at all, not a replacement for the directive's row-level relaxation.

**A pending migration refuses if the resulting schema has a foreign key that is not real**, whether or not a directive is present. Exactly ONE question is decided in JS; everything else about whether a foreign key's parent key is genuinely usable is decided by SQLite itself, not by re-implementing its rules:

- **JS decides only: what TYPE does the target resolve to, via `PRAGMA table_list`, compared CASE-INSENSITIVELY.** `findForeignKeyTargetTypeIssue` (originally `findMissingForeignKeyTargetTable`, existence-only; see the dedicated section below for why it grew a type check) walks every foreign key in the schema and resolves its target against the schema's real `main`-schema names, case-insensitively (SQLite itself resolves names that way). This one question cannot be delegated to SQLite: on the plain path, `.prepare()` reports a missing target only as a raw, unprefixed `no such table`; on the directive path, `PRAGMA foreign_key_check` with `PRAGMA foreign_keys` `OFF` never reports a missing target at all when the referencing table happens to be empty -- exactly the case this whole check exists for (see above). A failure throws `migration_foreign_key_check_failed:` (post-migration) or `migration_preexisting_structural_violation:` (pre-existing, see below), naming the migration, the referencing table, the target, and -- for a `view` or `virtual` target -- its type.
- **SQLite decides everything else about a `table`-typed target, via a PARENT-side probe.** For every DISTINCT existing target that resolves to a `table` (a `shadow`-typed target is deliberately skipped; see the dedicated section below), `findParentSideForeignKeyProbeFailure` prepares -- but never executes -- `DELETE FROM "<target>" WHERE 0`. Preparing a DELETE against the PARENT table makes SQLite resolve every foreign key any child table declares against it, in ONE statement per parent, regardless of which child, which columns, or how many constraints reference it; `WHERE 0` guarantees zero rows are ever touched even if the statement somehow ran, which it never does. If any foreign key naming that parent does not actually resolve, `.prepare()` throws a `SqliteError` synchronously, before anything executes -- rethrown as the prefixed `SchemaVersionError`, naming the migration, the parent table, and SQLite's own message verbatim, whether the message is `foreign key mismatch - ...` or anything else (e.g. an `ON DELETE` trigger on the parent referencing a table that no longer exists -- never left as a raw, unhandled `SqliteError`; see the dedicated section below for exactly how that message is now worded). This runs on the **plain path**, where `PRAGMA foreign_keys` is `ON` the whole time, for key resolution; it now ALSO runs post-exec on the **directive path**, where `PRAGMA foreign_keys` is `OFF` while the migration's SQL runs, but there it resolves nothing about foreign keys (the probe cannot do that with the pragma `OFF`) -- it is used there only to catch a broken trigger a rebuild left behind, which `PRAGMA foreign_key_check` (already run on that path both before and after the migration's SQL, and still the sole authority on key resolution while `PRAGMA foreign_keys` is `OFF`) cannot see at all, since it never inspects trigger bodies. See the dedicated section below.

**Two hand-written replacements for SQLite's own foreign-key rules were tried here and both disagreed with SQLite -- the durable fix stopped deciding anything beyond bare table existence in JS.** The first parsed each candidate parent key's declared collation out of its `CREATE TABLE` text and compared it by hand; against SQLite's own verdict on 27 real parent-key shapes it disagreed on 7 -- 6 false **rejections** (the text merely *looked* like it might mention `COLLATE`: inside a `CHECK` expression, a `DEFAULT` string, a block comment, or past an apostrophe or a stray `(` inside a `--` comment, or a quoted `"check"` column mistaken for the constraint keyword) and 1 false **acceptance** (`PRIMARY KEY (id COLLATE NOCASE)` on an otherwise-`BINARY` column, whose PRIMARY KEY short-circuit never compared a collation at all). The fix for that deleted the parser but replaced it with a JS pre-filter (table/column existence, "is this a key" by column-NAME matching) that ran a per-constraint, CHILD-side `UPDATE "<child>" SET "<col>" = "<col>" ... WHERE 0` probe only after passing that pre-filter -- and the pre-filter itself introduced five NEW false rejections: a case-different target column (`REFERENCES parent(ID)` against an actual column `id`), a case-different target table (`REFERENCES Parent(id)` against an actual table `parent`), a case-different UNIQUE index column (index on `Code`, FK names `code`), a `GENERATED` parent key column (`PRAGMA table_info` omits generated columns entirely), and a `GENERATED` child FK column itself (SQLite refuses to `UPDATE` a generated column at all, so that child-side probe could not even run against one). Both mistakes shared a root cause: deciding anything beyond bare table existence in JS, ahead of SQLite, risks disagreeing with SQLite's own rules. The parent-side probe above cannot fail this way -- it names no column at all, so there is no column-name or generated-column mismatch for JS to get wrong.

**The directive is still required, but only to relax row-level enforcement for a parent rebuild on a populated database.** Neither the missing-table check nor the parent-side probe can make the unsafe rebuild order safe when the referencing table already holds rows: `DROP TABLE` on a table other rows still reference is refused by SQLite itself while `PRAGMA foreign_keys` is `ON`, and that pragma cannot be turned off mid-transaction. A migration that rebuilds a table other tables reference by foreign key, once the database can already hold rows that reference it, still needs `-- msp-migration: foreign-keys=off` for that reason -- these checks on the plain path are a floor that catches the "empty table" case with no directive at all, not a replacement for the directive's row-level relaxation.

**Boundary: the check is schema-only, so a pre-existing structural defect blocks the next pending migration too -- but is no longer blamed on it.** BOTH the missing-table check and the parent-side probe also run once against the CURRENT schema, before `db.exec(file.sql)`, on both paths. On the directive path this runs before `PRAGMA foreign_keys` is ever turned `OFF`, so the parent-side probe is meaningful there too. If the schema was already structurally broken before this migration -- some earlier, already-applied migration, or out-of-band tampering, left a foreign key pointing at a missing table or an otherwise-unresolvable parent key (including a pre-existing table-level `PRIMARY KEY (... COLLATE ...)` mismatch, not only a missing table) -- that is reported distinctly, prefixed `migration_preexisting_structural_violation:` (naming the table and target) rather than `migration_foreign_key_check_failed:`, and the migration's own SQL never runs at all, mirroring the existing `migration_preexisting_foreign_key_violation:` guard for row-level violations on the directive path. If the schema was NOT already broken, and this migration's own SQL introduces the defect, the next pending migration after this one would still inherit and refuse on it too, since the check runs against the whole schema every time -- that part is not new. The real root schema (migrations `0001`-`0007`) is confirmed structurally valid under the new check, including the `entities_fts` FTS5 virtual table and its shadow tables, and a follow-on plain migration against that schema applies cleanly. An already-applied migration never re-runs any guard, including this one, so a database that is fully migrated today boots exactly as it did before this change.

### A foreign key's target has a TYPE, not just an existence bit (RKOI final review of the plain-path check, four warnings)

**"Does the target table exist" is not the same question as "is the target a TABLE".** SQLite's own `PRAGMA table_list` reports one of four values in its `type` column for every name in a schema: `table`, `view`, `virtual` (an FTS5-style virtual table), or `shadow` (a virtual table's own internal storage table, e.g. `<fts>_data`, `<fts>_config`). The case-insensitive existence check above cannot tell these apart, and confirmed against real SQLite, that was wrong in three different directions:

1. **A VIEW target was refused, but misreported as "does not exist".** A view genuinely cannot satisfy a foreign key -- SQLite itself raises `foreign key mismatch` the moment anything tries to resolve one -- but the existence check treated a view exactly like a missing table, which is a different, false claim.
2. **An FTS5 VIRTUAL TABLE target was WRONGLY ACCEPTED on the plain path.** Preparing `DELETE FROM "<virtual>" WHERE 0` against a virtual table compiles no foreign-key resolution code at all -- there is nothing for SQLite to check at prepare time -- so the parent-side probe reported no failure, the migration committed, and the server booted. The first real write to the referencing table then throws `foreign key mismatch` at runtime, and no later pre-exec check catches it either, since the probe never resolves a virtual target going forward.
3. **An FTS5 shadow table target was WRONGLY REFUSED on the plain path (for a real key column; see the pre-merge fixup below for a NON-key column, the opposite mistake).** This connection runs under SQLite's "defensive" mode (`SQLITE_DBCONFIG_DEFENSIVE`, a per-connection flag better-sqlite3 enables by default -- not something FTS5 itself sets), under which even a bare `DELETE ... WHERE 0` against a shadow table fails to prepare with `table "<shadow>" may not be modified` -- a genuine `SqliteError`, so the parent-side probe treated it as a real resolution failure. SQLite, however, resolves and enforces a real foreign key to a shadow table's declared PRIMARY KEY perfectly well at actual write time. Once a directive migration added such a foreign key, this false rejection also poisoned the pre-existing check for every subsequent migration, since the same probe runs there too.

**The fix resolves every foreign key's target through `PRAGMA table_list` (schema `main` only) instead of only checking bare existence.** A target absent from `main` -- including one that exists only in `temp.`, which SQLite itself would refuse to resolve as `no such table: main.<name>` -- is still "missing", worded exactly as before. A target present as `view` or `virtual` is a **new, distinct refusal**, naming the migration, the referencing table, the target, and its type (e.g. `... references "v", which is a view, not a table` or `... "items_fts", which is a virtual table, not a table`) -- on **both** paths, and checked before the parent-side probe ever runs, so the probe itself never has to deal with a virtual table's silent non-resolution. A target present as `shadow` **skips the parent-side DELETE probe entirely** -- that probe's defensive-mode DELETE failure was never a real signal about whether the foreign key resolves -- and is instead checked a different way, described in the pre-merge fixup section below: it is not simply "accepted outright". A target present as `table` is unchanged: probed exactly as before. Nothing here reintroduces `CREATE TABLE` text parsing or any column-/key-matching logic in JS -- the type question is answered by a pragma (a catalog fact), and everything about whether a foreign key actually resolves remains SQLite's call, via the parent-side probe (table targets), `PRAGMA foreign_key_check` (table-scoped, for shadow targets, or the directive path's row-level check).

### The directive path's post-exec checks now also run the parent-side probe (RKOI final review, warning 4)

**`PRAGMA foreign_key_check` says nothing about a DELETE trigger, on some table unrelated to any foreign key, whose body references a table this migration's rebuild dropped** -- that pragma only inspects declared foreign keys, never trigger bodies. Confirmed against real SQLite: preparing `DELETE FROM "<parent-with-the-trigger>" WHERE 0` still fails with a raw `no such table: main.<dropped>` even while `PRAGMA foreign_keys` reads `OFF`, because compiling a trigger's body is not gated by that pragma at all -- only foreign-key resolution is. The directive path's post-exec checks, inside the same `db.transaction(...)`, now also run the parent-side probe (`findParentSideForeignKeyProbeFailure`) after `db.exec(file.sql)` and the existing `runForeignKeyCheck`, the same check the plain path already ran post-exec. This does **not** duplicate key resolution: while `PRAGMA foreign_keys` reads `OFF`, the DELETE probe still does not resolve a foreign key (see above), so `runForeignKeyCheck` remains the sole authority for that; the probe is added here only to catch this trigger-shaped class of breakage. A directive migration that drops a table a parent's DELETE trigger references is now refused **post-exec**, prefixed `migration_foreign_key_check_failed:`, exactly like the plain path -- rolling the migration back so the next pending migration is never reached against a poisoned schema.

**A probe failure that is not a `foreign key mismatch` now says the parent table cannot be deleted from, not that "a foreign key SQLite refuses to resolve".** The trigger case above, and any other raw `SqliteError` preparing the parent-side DELETE, means the parent table itself cannot be deleted from for some other reason. The message now reads `... left table "<parent>" that cannot be deleted from -- SQLite reports "<SQLite's own message>"` for that case, and reserves "a foreign key SQLite itself refuses to resolve" wording for when the message actually contains `foreign key mismatch`. Every message stays prefixed either way; only the wording changed.

### Pre-merge fixup: a shadow target's own non-key column, temp-object shadowing, and internal SQLite targets (RKOI pre-merge fixup of the final review)

**Warning 1 (required): a foreign key to a shadow table's own NON-key column was wrongly accepted on the plain path.** Skipping `shadow` targets in the parent-side DELETE probe (above) only means the probe cannot ask whether such a foreign key resolves -- it does not mean every one does. A foreign key naming a shadow table's own non-key column, a column that does not exist on it at all, or an rtree virtual table's shadow table's non-key column is just as invalid as a `view` or `virtual` target and SQLite still refuses it with `foreign key mismatch` -- but nothing asked it to, so it committed, booted, and only the first real child write threw at runtime. Confirmed against real SQLite on four such shapes (an FTS5 shadow table's own non-key column, a nonexistent column on one, an FTS5 `_content` shadow table's non-key column, and an rtree virtual table's shadow table's non-key column), and confirmed to still accept the PRIMARY KEY shapes that must keep working. The fix asks the same question a different way: `PRAGMA main.foreign_key_check("<child>")`, scoped to the CHILD table declaring the foreign key rather than to the shadow table itself, which never touches the shadow table (no DELETE, no defensive-mode conflict) and still raises `foreign key mismatch` when the key does not resolve. Any ROWS this returns instead of throwing are deliberately ignored -- on the plain path row-level enforcement already happens per statement as it happens, so a pre-existing orphaned row must never block boot; only the mismatch *exception* is this check's business. This runs post-exec on the plain path and pre-exec on both paths, alongside the existing checks; the directive path's post-exec `PRAGMA foreign_key_check` (unqualified, whole-database) already raised the identical error for every one of these shapes regardless of `PRAGMA foreign_keys`'s value, confirmed against real SQLite, so it needed no change.

**Warning 2 (included): every unqualified object name this module asks SQLite to resolve is now schema-qualified with `main.`.** `PRAGMA foreign_key_list(<table>)` and the parent-side probe's `DELETE FROM "<target>" WHERE 0` are ordinary object-name lookups, resolved under SQLite's normal name-resolution rules, where a `temp` object of the same name takes priority over one in `main`. Confirmed against real SQLite: if the connection holds a `TEMP VIEW` (or table) sharing a `main` table's name -- created by some other part of the process before this module runs -- an unqualified `PRAGMA foreign_key_list` on that name silently returns the TEMP object's foreign keys instead of the real table's, and an unqualified `DELETE FROM "<name>" WHERE 0` resolves against the TEMP object too, which is how a same-named `TEMP VIEW` produced a raw `cannot modify <name> because it is a view` for a perfectly valid `main` table. `sqlite_schema` itself is exempt -- SQLite always resolves the bare, unqualified name to `main`'s own schema table, confirmed against real SQLite -- but nothing else this module asks SQLite to resolve gets that exemption. Every `PRAGMA foreign_key_list` call (including the new shadow-target check above) and the parent-side probe's `DELETE` are now written `PRAGMA main.foreign_key_list(...)` and `DELETE FROM main."<target>" WHERE 0`, so they always resolve against the real `main` table regardless of what the connection's `temp` schema happens to hold.

**Warning 3 (included): a foreign key to one of SQLite's own internal `sqlite_*` catalog tables (e.g. `sqlite_sequence`) is correctly refused, but is now attributed accurately.** `mainSchemaEntries` deliberately excludes `sqlite_*` names from its lookups -- they are never legitimate migration targets -- so such a target used to fall through to the "missing" case and claim the table does not exist, when it is very much present (SQLite refuses to resolve a key against it with `foreign key mismatch`, confirmed against real SQLite, because it has no usable key for a foreign key to target). `findForeignKeyTargetTypeIssue` now checks an *unfiltered* `PRAGMA table_list` reading before concluding "missing", and reports a distinct kind, worded "which is an internal SQLite table, not a valid foreign-key target" rather than claiming it does not exist. The refusal itself, and its prefix, are unchanged on both paths and pre-existing -- only the reason given is now accurate.

## Legacy stored data and the escaped-object-key transport scan

TASK-MEMOS-002 stage 2 added an engine-independent scanner
(`escaped-object-key-scan.mjs`) at every transport boundary, refusing an
inbound or outbound line whose object keys contain an escape sequence
(see `docs/NOTES.md`'s "V8 `JSON.parse` non-first-key corruption" section
for the full finding). That scan only ever protects requests and
responses going forward -- it cannot rewrite a row already written to
`entities`/`entity_history`/`journal`/`protected_memory_records`/`state`
(or any other JSON-bearing column) **before** this fix existed. A
deployment migrating from a pre-fix version should run the audit query in
`docs/NOTES.md`'s "Legacy stored data may already contain an escaped key"
section to check whether any already-stored JSON might be affected; no
migration step here rewrites such data automatically.

**This is not a complete guarantee.** The server's own `write()` refusal
only catches a response whose stored text STILL needs an escape to
round-trip through `JSON.parse` today. A legacy key already corrupted by
this same engine bug at write time into a key that happens to need NO
escaping (e.g. a two-letter key like `aA`) would round-trip cleanly and
be emitted as normal -- silently wrong, and undetectable by the scan.
Running the audit query and manually inspecting (and, where necessary,
repairing) any flagged row is the real remedy for data written before
this fix shipped; see `docs/NOTES.md` for the full explanation.

## Rollback

Revert the single dependency/re-export change and reinstall GoVibe dependencies. The original `packages/govibe-core/src/msp-client.mjs` and `msp-stdio-transport.mjs` remain available until the consumer cutover is independently accepted.
