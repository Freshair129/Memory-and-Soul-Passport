## 1. Purpose and scope

**Goal.** MSP becomes a complete memory runtime in which:

- every read and write is scoped to one tenant;
- a person's private memory is visible only to that person's own authorised context;
- two agents serving the same person keep separate episodic memory and share only what the model explicitly shares;
- all of the above is proven by suites that run through the real `msp-server` process.

**In scope.** MSP repository work only:

- the thread/session surface (API-011);
- principal vaults and `msp_vault_resolve` (API-010);
- the API-009 caller-identity amendment;
- participant and agent lifecycle;
- erasure and retention;
- consolidation;
- migration-runner follow-ups;
- the release.

**Out of scope for now.** Everything that needs a channel. Real-process LINE proof, the LINE canary and production summary hosting are `TASK-MEMOS-005..007`, parked in PH-MEMOS-8 by owner direction (2026-09-14). The same applies to any zuri-ai code change.

## 2. Identifier scheme

Every item carries exactly one id. Ids are keys: never renumber or reuse them. Mark a dropped item `cancelled` and keep its number burnt, following the zuri-ai convention in AGENTS.md §18.

| Family | Form | Meaning |
|---|---|---|
| Plan | `PLAN-MSP-MEMOS` | this document |
| Phase | `PH-MEMOS-<n>` | a stage with an exit gate |
| Gate | `GATE-MEMOS-<n>` | exit criteria of phase `n` |
| Sprint | `SPR-MEMOS-<nn>` | one delivery increment, ending in reviewed merges |
| Epic | `TASK-MEMOS-<nnn>` | the ten roadmap items in zuri-ai `ROADMAP.md` (rev 2.74.0b) |
| Backlog item | `BL-MEMOS-<nnn>` | an implementable unit with an owner, dependencies and proof |
| Decision | `DEC-MEMOS-<nn>` | an owner decision; DEC-MEMOS-01..16 confirmed by the owner on 2026-09-14 |
| Risk | `RSK-MEMOS-<nn>` | a tracked risk with a mitigation |

BL numbers are grouped by phase: 001–009 for phase 0, 010–019 for phase 1, 020–039 for phase 2, and so on. Gaps are reserved for items discovered inside that phase. **Where a phase's block is already fully allocated (2026-09-14 revision: phase 3's 040–049 has no free slot), a newly discovered item takes the next free number in the 100+ range instead of renumbering anything**; its Epic/phase columns still say which phase it belongs to. This is itself a convention change, recorded in this revision's CHANGELOG row rather than applied silently.

- **GATE-MEMOS-3** — every case below runs in `tests/security/thread-agent-scoping.security.mjs` unless noted (design §8, §15):
  - Agent B cannot read agent A's `AGENT`-visibility protected records; a `THREAD`-visibility record and every legacy (`agent_id IS NULL`) row are visible to both. Agent B recording content identical to agent A's `AGENT`-visibility record gets its **own** distinct record, not A's (`record_id`'s hash includes `agent_id`/`visibility`). **Superseding an unknown id, B naming A's `AGENT`-visibility record, and a record failing the pre-existing stage-1 ownership/status check are one identical answer** — `validation_failed` with the single fixed message "supersedes_record_id does not name a record this caller can supersede" — never three distinguishable codes and never stage 1's own `conflict` for the ownership/status case (corrected, RKOI stage-2 review round 2, superseding round 1's own `thread_scope_denied` fix, which was itself a third oracle value). `THREAD`-visibility and legacy `agent_id IS NULL` records stay supersedable by any agent under the stage-1 rules alone (CRITICAL 2, RKOI stage-2 review rounds 1–2).
  - A departed agent is denied `agent_not_current` on its very next call, on every thread-bound tool — `append`, `context`, `memory_record`, `injection_record`, `delivery_record`, `claim`, `commit`, `retry` — not merely `context`. **This is a per-call property of the agent gate, not a revocation control** (`DEC-MEMOS-18`) — the same departed agent can re-attach on its own `assertAgents` the very next call.

Two concurrent resolves for the same room produce exactly one auto-attached agent (the thread `INSERT` winner) — the loser never auto-attaches merely because its own lookup ran first (mint-race, RKOI stage-2 review round 1, item 9).

  - The journal actor is `grant.agentId` in plain text for agent-attributable entries (not a W5 regression — `agentId` is not personal data), and no raw principal id appears anywhere in the journal.
  - A replayed grant on any nonce-required tool (every mutating tool except `msp_thread_message_append`, and excluding the read-only `msp_thread_context`) is refused `grant_replayed`; a nonce-required tool called with no `nonce` claim is `grant_nonce_required`; a replayed nonce's transaction (mutation + nonce insert) rolls back together, never partially applying.

  - **`DEC-MEMOS-17`**: zuri-ai's current, unmodified grant (no `agentId`/`workspaceId`/`nonce`) is refused with a typed grant error — proven via `test:cross-zuri`, which the design and this plan state precisely: **before `BL-MEMOS-107` lands, `test:cross-zuri` asserts zuri-ai's `origin/main` grant is refused with a typed grant error; after `BL-MEMOS-107` lands, the same suite must pass against zuri-ai's updated port** — this is `test:cross-zuri`'s named suite for `GATE-MEMOS-2` as well as here, and the flip is a deliberate, expected change to what "green" means for that one suite, not a regression. The "wrapped port" case proves only that MSP *accepts the shape*, not that zuri-ai has actually adopted it — labelled that way in the suite and in `BL-MEMOS-047`'s acceptance.
